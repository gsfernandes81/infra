## How to work here

**Three playbooks, one per side, and none of them starts anything.**
`ansible/playbooks/dev-container.yml` (host), `cloudflare-dev-tunnel.yml` (edge),
`dev-client.yml` (a client). Lifecycle is `dev/Makefile` and stays there — the reason is
in the playbook's header and it is not merely a principle: the Makefile computes
`HOST_UID` from the *owner of the checkout*, and a second copy of that guard is one that
can silently build a container which writes root-owned files into the bind mount.

**Ansible runs from the phone, never from a Pi.** There is no `ansible` on `zero`, `one`
or `two` and there should not be. `ansible/README.md` opens with this.

**`gavin` is not in the docker group and `sudo` wants a password**, so nothing under
`dev/` runs from an agent session. Hand those over as a pasteable block. From the phone
they reach in one line: `ssh -t zero 'cd ~/infra/dev && make up'`.

**Only the phone's mobile radio is metered.** or3's `CLAUDE.md` § *Data budget* is the
rule and or3's `docs/data-ledger.md` is the record of what has already been bought. Work
from inside this container is free; the same work from Termux is not.

## What cost time today, so it does not cost it twice

Four failures reached the owner on a first real run. They share a shape worth naming.

- **A bootstrap play cannot dry-run the half that depends on what the first half would
  have created.** `--check` skips writes, but Ansible still *templates* a skipped task's
  arguments — so ids that only a write could produce are undefined and the render dies.
  Both `dev-container.yml` and `cloudflare-dev-tunnel.yml` hit this. The fix is an inline
  filler in the writes, never a `set_fact`: a fact makes the id look defined to the
  *reads* too, and reads run in check mode.
- **Cloudflare answers 201 on some creates.** `uri` accepts 200 alone by default, so a
  successful call failed the task — and because the response was `no_log`, the service
  token's one-and-only secret was censored and lost. Anything whose response cannot be
  fetched again must be printed *immediately* after it is created, not after the next
  three tasks.
- **The stubs kept agreeing with my assumptions instead of with the API.** They now
  return 201 where Cloudflare does and `null` where it does. Offline stubs are worth
  having and they are only as good as the shapes you gave them.
- **Nothing in this repo builds an image.** A Dockerfile ordering error — a `chmod` below
  `USER dev` against a root-owned file — was invisible until docker ran it on zero. That
  is the closed-loop gap, and this container is the thing that closes it.

`make verify` grew an `in-workspace:` line because of the last one; it checks the tools a
rebuild is supposed to have landed, and it should have been checking that one.

## Deferred on purpose, with the argument written down

**The container has no route to `zero`, `one` or `two`.** It ships ansible as a
*development* tool — syntax-checking a playbook — and is not wired to the fleet. Turning
it on would put the control plane inside a container on one of the boxes it controls, and
`management-plane.md` § *A control node inside the fleet* sets out the three objections
and the one good argument the other way, plus the three things that would change the
answer. Nothing in the repo builds it. Do not turn it on without reading that section and
putting the decision to the owner.
